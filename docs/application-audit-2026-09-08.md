# Application audit — 8 September 2026

## Arabic page-crash follow-up

The user subsequently reported Appointments failing while signed in as admin. The browser error overlay identified `TypeError: value.startsWith is not a function` in `translatePageText`, reached through `LocalizedText` in metric cards on Appointments and Vehicles. This was a rendering regression, not an access denial: `LocalizedContent` used `Children.map` on scalar children, replacing a string-valued component prop with an array. The wrapper now preserves scalar text/null/number/boolean children.

A new regression resolves `MetricStrip` before passing its tree to the client wrapper, matching the server-component composition that the earlier fixture missed. It reproduced the Arabic exception before the fix. Afterward, the English/Arabic regressions and recovery-layout checks passed in both configured test projects (6 checks total); lint and TypeScript also passed. Live Arabic Appointments and Vehicles loaded using the existing admin session without changing permissions or business records. These focused checks are not a rerun of the full application suite.

## Approved hardening follow-up — 8 September 2026

After the initial audit, the user explicitly approved the staged database change. Migration **20260908144433_audit_access_hardening** is now applied to the connected development project (70 applied migrations). No application deployment or business-data change accompanied it.

- Rechecked the application integrations: provisioning supplies authenticated JWTs/service-role credentials; public health endpoints do not access public tables. No anonymous/public RLS policies or anonymous-callable public SECURITY DEFINER functions were present.
- Captured exact ACLs before applying. The original information_schema count of 140 omitted 20 PostgreSQL MAINTAIN privileges: the true total was **160 ACL entries across 20 tables**. All are now removed. No public sequences existed. Postgres's default anonymous table/sequence grants are removed; Supabase-managed creator defaults and function defaults are outside this migration's scope.
- All non-anonymous public object grants retain the same before/after fingerprint, `2f125449f9f8815924ac92295ece91f9`. Authenticated/service-role access was not revoked. Portal policy access logic is unchanged; only `auth.uid()` evaluation is optimized. The targeted performance advisor warning is cleared.
- Post-migration suites passed: `tests/audit-access-hardening.sql`, `tests/audit-payment-replay.sql`, and `tests/inspection-due-followups.sql`. Fixtures rolled back; a subsequent query confirmed zero retained synthetic organizations.
- The first new portal test incorrectly assumed direct table access. Inspection showed the pre-existing customer_accounts RLS restricts those direct reads, while the actual portal reads via `portal_service_options`. The corrected test runs under the real authenticated role, verifies staff access, each portal's own RPC results, revoked-account denial and anonymous table denial. It does not broaden direct customer-table access.
- Emergency rollback now includes all 160 privileges, exact affected default privileges and the original policy: `tests/fixtures/audit-access-rollback.sql`. It restores the earlier weaker permission posture and is not an integration workaround. No rollback was needed.

The remaining operational/product gaps below are unchanged. The initial-audit measurements and 301-test application run predate this database-only follow-up; the three database suites were rerun afterward.

## Scope and evidence

Audited the current working tree, not just HEAD. Pre-existing UI, staff-management, inspection, follow-up, and module-removal changes were preserved. No commit, push, deployment, real payment, customer message, or permanent business-record mutation was performed. The two database regression transactions used synthetic users/organizations/records and rolled back.

This is a broad code/configuration, database, and runtime audit, **not certification that every feature or production integration works**. Verification limitations and unfinished journeys are listed below.

The application uses Next.js 16.3.4 App Router/server components and React 19.2.8. Server Actions validate form input and call Supabase using the signed-in user's SSR session. Postgres RLS restricts reads; permission-checked command RPCs enforce write invariants, optimistic versions, audit records, commercial state transitions and outbox events. Auth provisioning uses Edge Functions. English/Arabic client components share a cookie-initialized locale; operational pages now translate during rendering, not by changing React-owned DOM.

The current product starts with maintenance/bodyshop work orders, followed by assigned inspection checks, selected services/spare parts, pricing/approval, execution, and billing. Customers, vehicles, branch/staff access, inventory, purchasing, records and follow-ups support this flow. Historical HV/diagnostic schema remains for retained records; those standalone application modules are retired. Older specification/release documents described a broader product and should not be read as current acceptance evidence.

## Findings and implemented fixes

| Severity | Finding and cause | Fix and supporting evidence |
| --- | --- | --- |
| High | Payment/stock actions generated a new idempotency key on every invocation, defeating database deduplication when the same submission was replayed. | Generate a UUID with each rendered form and require that key in payment, stock movement, disposition, purchase receipt and transfer receipt actions. Action regression proves the same payment form retains its key and an expired form makes no RPC. Synthetic SQL proves duplicate receipts/allocations are not created and the balance remains correct. A newly loaded form has a new key; this does not deduplicate a deliberately new submission. |
| High | Customer portal login redirected inside a `try`; Next's successful redirect was caught as an authentication error. Expired/inactive sessions could lose record context or bounce between login and staff pages. | Move successful redirect outside the catch, reject inactive staff profiles, keep login public even with stale cookies, preserve a validated same-origin return path and cleared cookies, fail closed on Auth errors. Runtime tests cover portal/staff/inactive accounts, unsafe return paths and Auth failure. These use mocked Auth, not real credential login. |
| High | Page-wide `MutationObserver`/layout-effect translation changed server HTML before streamed children hydrated. Live logs showed mismatches on estimates, inventory, purchasing, quality, finance, records, staff and dashboard. | Replace DOM mutation with render-time React child translation at each of 22 server-page boundaries. Preserve input values, code and `bdi` content. New SSR regression tests verify translated initial markup. Revisiting the affected live routes produced no new hydration errors; Arabic mobile switching/reloading also produced none. |
| Medium | Invalid calendar dates were normalized silently; DST gaps/overlaps were accepted ambiguously. Portal appointment requests interpreted local values in the server's timezone. | Strict wall-time/calendar validation and round-trip timezone conversion. Portal resolves timezone through the authenticated `portal_service_options` RPC, then converts both endpoints. Tests cover Amman conversion, invalid dates, DST gap/overlap, and unauthorized branch rejection. |
| Medium | Cancelled inspections could be selected as the order's active continuation; explicitly linked accessible inspections could disappear under the operating-branch filter. | Continue the latest non-cancelled inspection. Resolve explicit inspection IDs from the RLS-scoped result set independently of the list filter. Verified an existing inspection deep link loads; backend branch authorization remains authoritative. |
| Medium | Duplicate customer-phone feedback redirected inside a `try` and was replaced by a generic error. | Throw the validation result and redirect once through the normal action-error path. Source-traced fix; no real duplicate contact was submitted. Database uniqueness remains necessary for concurrent submissions. |
| Medium | Unexpected page/session-query errors had no application recovery UI; branch/profile/permission query errors could masquerade as absent data/access. | Add route/global error boundaries, bilingual retry/sign-in actions and loading state. Access lookup failures throw to recovery rather than granting empty/default access. Build/type checks and recovery-layout tests cover the new components. An actual disconnected-network retry sequence was not exercised. |
| Low | Repeated branch reads across access resolution, layout and CRM pages; all service versions fetched before client-side selection filtering. | Share a request-local React-cached active-branch query. Filter service versions by selected IDs in the database and omit that query when none are selected. No cross-user persistent cache was added. Measurements below. |
| Low | README/release status claimed obsolete migration counts, removed modules, and blanket verification. | Replace current-status claims with dated evidence and this audit's explicit operational gates. |

## Workflow and trigger map

| User/system trigger | Execution and data changes | Visible outcome / boundary |
| --- | --- | --- |
| Open protected route | Request proxy verifies claims; `getCurrentStaff` loads active identity, memberships, capabilities and branch access. Server components issue RLS-scoped reads. | Page or safe login return URL; Auth/query failure cannot grant access. |
| Submit login | Mobile/PIN normalization → Supabase password sign-in → staff membership/profile or portal identity lookup → redirect. | Original allowed staff destination or `/portal`; inactive accounts sign out. |
| Change operating branch | Operating-branch endpoint validates membership, saves selected-branch cookie and refreshes the route. | Branch fields are locked to that selection; hidden values support actual form submission. Database authorization still applies. |
| Create/edit/archive CRM or staff record | Server Action validation → scoped RPC or provisioning Edge Function → audit/lifecycle changes → revalidation. | Record details, confirmation or error. History-retaining archive is distinct from irreversible deletion. Edge provisioning was inspected, not invoked in this audit. |
| Open maintenance/bodyshop order | Work-order intake action → order command; associates customer, vehicle, branch and reported issues. | Order workspace links to inspection and services/parts. Types use separate configured service catalogs. |
| Assign / select / generate inspection | `inspection_workflow` commands validate assigned technician and applicability, snapshot selected definitions and generate pending tasks. | Checklist; generation does not automatically pass checks. Cancellation no longer becomes the default continuation. |
| Save result / retest / review | Result command checks assignment/admin-on-behalf, expected attempt, findings and required fields; appends immutable results. Review completes inspection and advances checked-in order to diagnosis. | Pass/fail state and history. Review is an explicit trigger: merely starting an inspection does not advance the order. |
| Select required services | Inspection service-choice command stores selected published service-version references and description snapshots. | Choices appear on work order; adding quantities/prices remains explicit. Selection is not automatic stock issue or job execution. |
| Prepare order / add service or part | Estimate/invoice draft command → line and total recalculation. | Services/spare-parts ledger. Part pricing does not issue inventory. |
| Send estimate / record decision | `send_estimate` locks offer and moves eligible order to awaiting approval; staff/portal decision command records evidence and updates approval/order state. | Read-only offer and decision history. Approved lines do **not** automatically become invoice lines/jobs; see open decisions. |
| Start/finish assigned job | Version/assignment checks → timer/labor entry and job state update → audit. | Running/completed job. Synthetic SQL tested timer attribution and unassigned-staff rejection. |
| Receive/issue/transfer/count stock | Authorized inventory/purchasing RPCs validate quantities and references, update stock ledgers, and use form-retained replay keys for affected receipt/movement commands. | Inventory/receipt state. Physical stock operations were not submitted against business records. |
| Create/post invoice | Draft creation and explicit lines → `post_invoice` version check, totals/document number/hash and `invoice.posted` outbox row. | Immutable posted invoice. Synthetic SQL tested one posting event and stale-edit rejection. Queueing is not fiscal authority acceptance. |
| Receive payment | `receive_invoice_payment` locks invoice, checks permission/outstanding balance/idempotency, inserts receipt/allocation, updates paid total. | Partially paid/paid state. Synthetic SQL tested duplicate replay, overpayment and cross-tenant rejection. No payment-provider call. |
| Enter inspection due date / reschedule | Result command upserts one open recommendation per source task; `reschedule_vehicle_followup` checks timestamp and permission. | Upcoming/overdue items on vehicle/customer pages and call links. Synthetic SQL tested date persistence, retest deduplication and stale rescheduling. |
| Contact customer / queue message | Staff call link opens telephone handler; explicit message action validates consent and queues an outbox event. | Manual contact or queued status. No automatic due-date sender/scheduler is deployed or verified. |
| Portal appointment request | Authorized options lookup → branch-local to UTC conversion → `portal_request_appointment` ownership/window validation → waitlist/outbox entry. | Request awaiting branch scheduling, not a confirmed appointment. |
| Download record document | Staff/portal document route validates identity and scope, then renders document or creates private-storage signed link. | Scoped document response; not unrestricted public storage. Representative boundary tests exist, but no exhaustive private-file download audit. |

## Performance evidence

- Before edits, code had three independent branch-list reads on Customers/Vehicles: access resolution, layout and page. Query statistics also showed repeated branch variants (439 ID-only calls, 277 full calls, 175 short calls in the initial sample; respective mean DB execution times approximately 1.03/1.35/1.89ms). These are cumulative development statistics, not a page-latency benchmark.
- After request-local deduplication, one isolated authenticated Customers page load increased full-branch query `4213216660271054065` from **280 to 281 calls**. This supports one query for the measured load versus three code paths before. No claim of a measured end-to-end percentage latency improvement.
- Maintenance service lookup now requests selected version IDs only, and makes no service-version request when none are selected. No before/after byte or latency measurement was collected.
- Removing full-subtree DOM observers avoids their repeated translation work and the observed hydration recovery rerenders. CPU savings were not profiled.
- Database advisor reported 226 informational unindexed-FK candidates and 39 informational unused indexes on a small development dataset. No speculative indexes were added. The repeated `auth.uid()` evaluation warning was subsequently cleared by the approved hardening migration above.
- Final production build succeeds. Build duration is not presented as a page performance improvement. Large-dataset performance and Core Web Vitals still need representative production/staging traffic.

## Open issues and decisions

1. **Resolved after approval — database privilege hardening.** Initially blocked pending integration review and user approval; now applied and verified as documented above. No anonymous disclosure was demonstrated. The exact rollback snapshot includes the additional MAINTAIN privileges missed by the initial information_schema count.
2. **High operational gap — no automatic customer reminder delivery.** Follow-ups and manual contact are functional, but pg_cron is not installed and no active sender was verified. Choose a messaging provider, consent/template policy, scheduling timezone and delivery/retry ownership before enabling automatic outreach. No Codex personal automation was created for this application feature.
3. **Medium product gap — approved services → jobs/invoice is still manual.** `create_invoice_from_repair_order` creates an empty draft; approval does not copy priced lines or instantiate jobs. Confirm whether billing must copy only approved groups, how revisions/supplements affect existing jobs, and when stock should be reserved/issued. Automatically inventing that accounting behavior could duplicate charges or unapproved work; no financial conversion rule was fabricated.
4. **Medium scale risk — capped list/search completeness.** The configured PostgREST row limit is 1,000, while several pages fetch broad lists and then filter in application memory. Customer/vehicle deep links outside a truncated list can fail to resolve. Representative-volume server-side search/pagination and separate by-ID detail retrieval remain necessary; this audit did not claim them fixed or load-test beyond that cap. Nested history queries can also grow considerably.
5. **Security/operations:** leaked-password protection is disabled (advisor warning). Production MFA/PIN policy, rate limiting, monitoring, backup/PITR restore drills and file malware scanning require configuration/operational verification. Auth SECURITY DEFINER advisor warnings should be reviewed per RPC, not fixed by disabling the application's intended command boundary.
6. **External systems unverified:** payment webhooks/provider settlement, message delivery, fiscal integration acceptance, licensed vehicle service data and Edge Function provisioning. Outbox rows/adapter placeholders alone do not prove an integration is connected.
7. **Test coverage:** legacy `supabase/tests/transactional_workflows.sql` still contains retired HV scenarios and environment-derived existing identities. It was not treated as a current clean acceptance suite. No broad destructive/load test, actual account deletion, production migration, physical-stock movement, real fiscal invoice or real payment was performed. Mobile Safari/Firefox and real staff/customer credential flows remain unverified.
